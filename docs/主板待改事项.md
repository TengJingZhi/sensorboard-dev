# 主板（esp-cam）后续待改事项

本文档由从板（sensorboard-dev）适配过程中整理，供主板侧后续修改参考。  
本次从板已按以下协议实现：**UART payload = 11 字节，前 7 字节为振动开关状态，后 4 字节为激光累积状态**。

```text
payload[0..6]  = isCrashed[0..6]   // 7 个振动开关，屏蔽期内持续为 1
payload[7..10] = isCovered[0..3]   // 4 个激光开关，触发后累积保持为 1
```

从板发送策略：变化触发 + 周期心跳（默认心跳 200ms，最小发送间隔 10ms）。

**流程开始条件（三次握手）**：从板上电后只监听、不发送；通过三次握手确认后才开始正式上报：

```text
主板(esp-cam)                       从板(sensorboard-dev)
    │                                   │
    │── 0x02 START_REQ ───────────────→│  第1步：主板请求开始
    │                                   │
    │←──────────── 0x04 START_ACK ────│  第2步：从板确认就绪
    │                                   │
    │── 0x05 START_CONFIRM ───────────→│  第3步：主板最终确认
    │                                   │
    │   flowStarted = true              │
    │   开始处理传感器数据               │
```

三帧格式（均为 0-payload 控制帧）：

```text
START_REQ    | 0xAA | 0x55 | 0x02 | 0x00 | 0x02 | 0x0D |   (主板→从板)
START_ACK    | 0xAA | 0x55 | 0x04 | 0x00 | 0x04 | 0x0D |   (从板→主板)
START_CONFIRM| 0xAA | 0x55 | 0x05 | 0x00 | 0x05 | 0x0D |   (主板→从板)
```

对应字段：

- `0xAA 0x55`：帧头
- `0x02/0x04/0x05`：消息类型
- `0x00`：payload 长度 0
- checksum = `msgType ^ 0x00 = msgType`
- `0x0D`：帧尾

主板特性：2 秒超时重发 `0x02`，最多重试 5 次后放弃；比赛结束后重置握手状态允许重开。  
从板特性：被动响应——收到 `0x02` 即回 `0x04`，收到 `0x05` 即开始比赛；收到重复 `0x02` 时若已在比赛中则先重置再回 ACK。

## 1. 主板接收方式：建议改为中断接收（对应讨论 5.1）

当前主板 `esp-cam/src/UART_CAM.cpp` 是在 `loop()` 中轮询 `uartCamLoop()` 接收。

建议后续按技术参考改造为：

- 使用 UART 中断接收；
- 中断服务程序只做两件事：
  1. 将收到的 11 字节数据写入全局变量（如 `g_rx_data[11]`）；
  2. 置新数据标志（如 `g_new_data_flag = 1`）。
- 禁止在中断中做判断、拍照、图像处理；
- 主循环检测到 `g_new_data_flag` 后：
  1. 关闭中断/临界区保护下拷贝快照；
  2. 清除标志；
  3. 后续所有耗时处理基于快照进行。

> 当前轮询方式不影响从板发送协议，但从板在屏蔽期内持续上报同一位为 1，如果主板处理较慢，轮询可能积压多帧，因此建议后续改中断 + 快照。

## 2. 主板振动事件去重（对应讨论 5.2）

当前主板 `processFrame()` 中处理振动后：

```cpp
for (int i = 0; i < CRASH_SENSOR_NUM; i++)
{
    isCrashed[i] = false;
}
```

这只是把主板本地数组清零，**没有记录“这个振动事件已经处理过”**。

但从板会按照约定，在振动屏蔽期 `T_block` 内持续把同一振动位上报为 `1`。如果主板拍照冷却结束后再次收到同一振动位仍为 1，可能会重复执行撞墙拍照和扣分。

建议主板增加去重：

- 记录最近一次已处理的振动编号 + 处理时间；
- 或维护“已处理振动事件”标志，只有振动位从 0 → 非 0 时才允许处理；
- 或要求从板振动位清零后才允许处理下一次振动事件。

## 3. 主板激光防循环拍照（对应讨论 3.4）

当前主板 `processFrame()` 中检查：

```cpp
if (receivedCovered[i] != isCovered[i])
{
    coveredChanged = true;
}
```

如果从板一次性把多个激光位累积为 1，但机器人当前位置只允许采信前 1/2/3 位，那么未采信的位会一直与主板 `isCovered` 不同，导致主板每个拍照冷却周期都重复拍照。

建议主板增加防循环机制，例如：

- 对同一个未确认的 `diff` 设置最小重拍间隔；
- 或只有机器人位置较上次拍照发生变化时才重新拍照；
- 或对长期无法确认的激光位做标记，避免持续拍照。

## 5. 讨论内容

### 5.1 主板接收方式

参考里写“主板使用中断接收”，但当前主板仍是 `loop()` 里轮询 `uartCamLoop()`。这不影响从板发送协议，但如果后面要严格按参考改成中断接收，主板还需要再改。从板这边不用等它。

### 5.2 主板振动去重

当前主板处理完振动后会：

```cpp
for (int i = 0; i < CRASH_SENSOR_NUM; i++) isCrashed[i] = false;
```

但它没有记录“这个振动事件已经处理过”。如果从板按你的要求在整个 `T_block` 内持续上报同一个振动位为 `1`，主板在拍照冷却结束后可能再次看到该位为 `1`，从而**重复处理同一个振动事件**。

所以需要二选一：

- 主板增加“已处理振动事件”去重（例如记录 `lastProcessedCrashIndex` + 时间，或等振动位清零后再允许下一次处理）；
- 或者从板把 `T_block` 设得比主板拍照冷却 `1s` 短，但这和你参考里的 `T_block > T_comm + T_cam + T_img + margin` 冲突。

我倾向：**从板按参考保持振动位持续为 1，同时主板补一个简单去重**。

### 5.3 主板激光重复拍照

当前主板 `coveredChanged` 判断的是“从板累积值”和“主板 `isCovered`”是否不同。如果从板一次性把 4 个激光位都累积为 1，但机器人位置只支持采信前 1/2/3 位，那么剩下的位会一直和主板 `isCovered` 不同，导致主板**每隔 1 秒就重复拍照**。

参考里也提到了“防止循环拍照”。这个属于主板侧后续优化，但从板侧可以把激光累积值按实际触发顺序/位置分批发，避免一上来全 1。具体要看赛道激光布局。


### 5.4 几个时序参数

| 参数 | 建议值 |
|------|--------|
| `T_block` 振动屏蔽 | 2000 ms |
| `T_heartbeat` 心跳 | 200 ms |
| `T_min` 最小发送间隔 | 10 ms |
| 激光判定阈值 | 512（可配置） |

## 6. 最终从板状态机

```text
初始化：
  vibration_active = -1        // 当前锁存的振动编号，-1 表示无
  vibration_block_until = 0
  laser_acc[4] = {0,0,0,0}
  last_send_time = 0

loop：
  1. 读 7 路振动
     - 若 vibration_active == -1：
       - 找到第一个为 1 的振动 → vibration_active = i
       - vibration_block_until = now + T_block
     - 若 now >= vibration_block_until：
       - vibration_active = -1，清振动输出
     - 输出 vibration_active 对应位 = 1，其他 = 0

  2. 读 4 路激光即时状态
     - laser_acc[i] |= laser_instant[i]

  3. 组帧：payload[0..6] = vibration_bits
            payload[7..10] = laser_acc

  4. 发送条件：
     - 距上次发送 >= T_min
     - 且（数据有变化 或 距上次发送 >= T_heartbeat）
```
